# NapCat 接入与隔离设计

自有文档 MIT。基于 `历史修订` 的设计已按用户要求编码；2026-10-27 后续已实现本仓库strict合同、ProcessIsolationBridge、独立worker及媒体v2接线，并做本地namespace／loopback测试，生产隔离尚未验收。没有修改已安装插件、生产配置或连接真实 QQ。现状见 [开发状态](开发状态.md)，历史见 [开发日志](开发日志.md)。

## 通道职责与身份合同

保留现有单一 OneBot11 正向 WS 接入。NapCat 校验连接登录账号及事件 self_id，适配器校验消息种类、用户／群精确 ACL、真实 at segment、发送者一致性后才构造 `MessageEvent` 并调用宿主 `handle_message`。原生 source 传 platform、user_id、chat_id、chat_type、message_id；线程只有宿主与协议确有可信来源才传，不能从正文推断。

`dm:<用户ID>` 与 `group:<群ID>` 区分来源，名称用 `display_identity` 展示；nickname/card/friend_remark、channel_context、引用正文与群 role 都不能决定身份或权限。引用 ID 不代表有权读被引用的历史，不自动拉取跨来源消息。OneBot 服务和 token 若失陷可伪造协议身份，因此该服务仍在受信任边界内，不能声称 QQ 成员端到端签名认证。

不要为做记忆而把任意事件 metadata 塞进原生准入合同；当前只用宿主支持的 source／event 字段。新增可信字段需先核对宿主契约及异常拒绝，避免 invalid_params 或授权字段被丢弃。模型不参与身份解析。

## 私人／社交路由

私人 default 继续保留原有功能，社交域共用一个受限执行环境，内部按可信用户与来源隔离，不为每位群友建 profile。当前 `group_sessions_per_user=true` 已开启，沿用其按人会话基础；不是所有群成员必然共用一份上下文。公共话题通过明确的群公共记忆补充，不合并私人历史。

以下为语义表，不是生产配置或本轮操作指令；全部使用占位标识：

| 可信事件 | 必须同时匹配 | 目标及约束 |
| --- | --- | --- |
| 主人私聊 | platform=napcat、chat_id=`dm:<OWNER>`、user_id=`<OWNER>`，入口核对 chat_type=dm | 私人 default，沿用主人权限 |
| 允许群中任何已授权用户（包括主人） | platform=napcat、精确 `group:<ALLOWED_GROUP>`、用户 ACL、真实 @ | 社交域，不能读取私人 builtin／Mem0 |
| 经后续批准的访客私聊 | platform=napcat、精确 dm 与同一 user、访客策略 | 社交域，不能回落私人域 |
| 未知／缺字段／目标不可用／不一致 | 不接受宽泛默认规则 | 拒绝；不调用模型，不建私人会话 |

本机 `gateway/profile_routing.py` matcher 支持 platform/chat_id/user_id 等字段，没有 chat_type；声明字段按 AND 匹配，按 specificity 排序，其中 user_id 权重 16、chat_id 权重 4。一个宽泛 owner user_id 规则可能比群规则更具体，从而把主人群聊误送私人域。必须精确限定 owner 的 dm chat_id，不能只说“把群规则排前面”。`match_profile_route` 未匹配时返回 None；是否拒绝由调用方决定，配置规则本身不能证明 fail closed。

本轮补查同一宿主 HEAD：`gateway/run.py:_profile_name_for_source` 对已匹配但未服务的 profile 抛 `ProfileRouteRejected`，`build_source` 保留拒绝标志，`_drop_unresolved` 有拒绝路径；未匹配仍返回 None，某些 profile home 异常仍回落，因此不能把已有 unserved 拒绝泛化为完整隔离。profile 初始化失败及 agent 缓存仍需验收。在进入私人上下文加载前必须统一强制策略，任何错误均不回落 default。

本仓库新增 `isolation.py:IsolationPolicy` 直接解析受信任 source：主人精确私聊走私人域，全部允许群聊走社交域，访客私聊另需显式清单。名称、role、宿主已写入的 profile 不决定路由。没有协议可信线程，strict 拒绝 thread／parent 来源，不猜测线程归属。它只确定目标，不证明宿主已经按目标隔离。

## 宿主准入与执行域

入站 ACL → 精确路由 → 域配置／工具能力验证 → 会话和 agent 构建 → 记忆提供者，是所需顺序。当前适配器已有前一层，后续层需宿主扩展或经过验证的可中止 middleware；普通 fail-open 观察钩子不能替代。验证失败必须在 builtin MEMORY/USER、技能、历史和缓存 agent 被加载之前返回明确拒绝。

已实现的 strict 接线是代码构建的 `IsolationBridge`，不是 metadata 或配置自证：`admit(Route)` 校验宿主能力后返回绑定同一不可变 Route 的 Admission，`dispatch(event, admission, reply)` 独占执行。无 bridge 时 connect 拒绝且入站不处理；拒绝、超时或异常均不回落私人 `handle_message`。正常平台factory当前使用显式host_llm／contract4，真实probe验证prepare-only worker后通过正式ctx.llm调用；主人DM单独保留native生命周期。显式all_members仅在白名单群开放普通成员，须匹配公共bridge合同1；新模式没有社交记忆／工具，不加载私人agent。当前昵称作为单次JSON数据传递，源码与离线验证不能替代现场验收；部署由父任务处理，见 [群权限与昵称](群权限与昵称.md)。

社交域默认仅开放聊天和受控 scope 记忆工具。终端、任意文件、session_search/history、技能和项目加载、cron、delegate、管理命令及任意出站发送需要显式能力控制。所有子任务、后台回调和定时任务必须继承不可变域和受限权限，缺上下文就拒绝；不能以工具参数 home 或模型声称 owner 来提升权限。开放 web 等工具也需独立审核信息出站。

同进程多 profile 不是 OS 沙箱。较强隔离建议独立系统账号／容器执行社交请求，禁止挂载私人 home／凭据／state.db；可信入口持有单个 NapCat 连接，只把最小消息和验证身份交给社交执行域。具体消息传递必须认证、防重放、有界队列和限定回复目标，不能让执行域指定任意 QQ 目标；实现前另行评估宿主能力。不能简单让两个网关/profile 同时连同一个机器人。

## 会话、缓存与失败

agent 缓存键至少包含域、精确来源／用户及 policy revision；切换路由不能复用已含私人提示词的 agent。社交新建干净会话，私人旧历史保留；摘要、压缩、引用、重置、重启恢复与历史搜索均须检验归属。昵称变化不得改变 principal 或开新权限，message_id 也不能单独作为跨群幂等键。

不可变 `Route.session_key` 已包含上述域、profile、策略、来源和用户，实际宿主缓存仍需使用它并验收。strict 回复闭包只绑定当前来源及原消息，dispatch 返回或取消后撤销；即使后台继承 ContextVar 也不能迟到发送。并发请求的回复上下文相互隔离。原有 legacy 发送 API 行为不变。

隔离前提不满足时拒绝请求；记忆服务单独失败而隔离仍成立时才允许显式“无记忆聊天”，不切主人 Mem0、不降低工具限制。适配器连接故障按现有重连处理；未知／部分发送结果不能自动重发以免重复公开信息。当前协议层有界内存队列和短期去重，尚无持久入站／出站消息保证；记忆 outbox 的可靠性不能冒充 QQ 投递可靠性。

运行观测只记录匿名域、路由结果、拒绝原因、队列深度和错误码，避免原文、QQ／群号、token 或第三方完整响应。只读状态必须区分“连接成功”“账号匹配”“消息已接收”“模型已完成”“QQ 客户端确认送达”，不以单个 OK 代替端到端结果。

## 与记忆插件的接口边界

通道只传宿主支持的可信来源，不调用 embedding、不选择模型、不直接读 SQLite。scoped-memory 在每次调用重校验用户／来源，local-only 社交模式永不创建主人 Mem0；公共群事实策略在记忆服务内执行。向量失败只影响召回，不能改变通道路由、用户 ACL 或发消息目的地。详细数据方案见 [分域记忆开发设计](../../hermes-scoped-memory/docs/开发设计.md)。

参考 [dafeiyu-astrbot](https://github.com/whyever77/dafeiyu-astrbot) 的身份展示与按会话组织思路，已只读核对其包装插件入站身份标签和按会话冷却的相关代码。但它基于 AstrBot 并依赖 LivingMemory，标签写入文本不能直接映射为 Hermes 安全边界。包装项目 MIT 与实际记忆依赖 AGPL-3.0 分开；本方案不复制其实现。具体源码来源、借鉴和差异集中在分域记忆设计，避免重复维护两套模型选型。

## 实施与验收清单

1. 先在新隔离 home 与合成事件测试路由：主人 dm、主人群聊、访客 dm、允许／未知群、缺字段、伪造 nickname/card、交叉 thread、重放与 target profile 故障。
2. 证明未知路由、失效提供者及拒绝 middleware 不会继续调用私人 agent；观测 builtin、文件、history、技能、delegate、cron 均无私人泄露路径。权限测试必须包括恶意工具请求，不仅模型口头拒绝。
3. 验证单连接分发、并发顺序、发送目标绑定、断线／超时／部分发送，不启动第二个生产连接。验证会话压缩、重置和缓存失效后仍按人／域隔离。
4. 在获得后续明确授权后，以真实 QQ 多账号做主人私聊、主人群聊、访客、跨群及未知身份验收；客户端人工核对实际回复内容与公开范围。现有真实通道基本使用不能替代这些新场景。
5. 用户审查结果后才部署、切换或扩大白名单；保留回滚接线方案、私人数据和单一连接所有权。本轮不执行上述部署步骤。

2026-10-27 初期以合成测试 bridge 验证精确路由、无 bridge／异常拒绝、目标绑定、策略版本键、并发和取消后能力撤销；后续已新增 `ProcessIsolationBridge` 与实际 bubblewrap 独立 worker，并以本地模型假服务验证挂载／环境／工具边界。媒体任务进一步扩展 `media_contract=2`：准入后获取与无网络解析，派生内容通过独立合同交给原对话模型，不进入命令解析、记忆或持久历史；缺旧／新合同均不降级私人路径。具体能力与路径修复后两种TMPDIR各自88＋5自动化结果见 [媒体实现与验收](媒体实现与验收.md) 和 [开发状态](开发状态.md)。这些不构成真实云模型、私人完整回调或第4项客户端验收。普通工厂未部署，跨进程单连接所有权与持久消息投递仍未实现。

独立执行体与公共事件确认已有本地实现，真实部署接线、身份和媒体出口仍待审查与授权验收；不能仅据静态核对或本地假服务承诺生产隐私验收。

R1／R2安全返修进一步将媒体模式的普通strict文本、取消控制与媒体任务分别有界分发，本地probe不与模型共用semaphore；同一认证OneBot消费者不再等待慢文本完成才接纳撤回／取消。文本同chat FIFO，跨通道不承诺总回复顺序；所有回复仍绑定原来源。选择来源在入队冻结，缺失／歧义不能随后来附件改变，执行时重新核验TTL、scope、权限、策略和撤回。9项定向与97＋5完整本地回归通过，修复前失败证据和限制见开发状态；仍待父任务独立复核。
