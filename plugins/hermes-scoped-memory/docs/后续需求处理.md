## 公共事实如何确认

工具仅暴露 `public_propose`、`public_pending`、`public_lookup`、`public_withdraw`。`ConfirmationAuthority` 留在可信宿主代码，签发实例绑定、限时、一次性 grant；修改工具参数不能取得 grant。确认绑定事实 ID、完整内容、来源、policy revision 和事实 revision，不能拿旧确认覆盖新版本。

隔离 worker 提供实际的原始用户命令入口（不会执行模型输出里的命令）：

```text
/memory-propose 合成项目 | 合成项目周五发布
/memory-confirm <提案ID> <当前确认卡的摘要>
/memory-resolution <冲突提案ID>
/memory-resolve <冲突提案ID> <当前决议卡的摘要>
/memory-withdraw <本人的贡献ID>
/forget <本地记忆ID>
/forget-all
```

确认卡展示完整公共陈述及确认命令。确认者必须属于 `public_group_memory.confirmers` 中**精确群／线程 → canonical principal** 的列表；冲突决议另用 `resolvers`。没有白名单就拒绝，不把群 role 或“主人”昵称当权限。`/forget-all` 只清当前本人＋当前来源；不会删除其他人或其他群的数据。

“A 说 B 会来”仍是 A 的陈述；B 确认保存为另一份来源。简单“确认”只证明批准，不提供独立全文证据：A 删除其贡献后公共事实暂停，不能把 B 的空白确认重建成原来的全文。仅剩余已批准、包含完整内容的独立贡献可重建，冲突必须另走可信决议。

## 可运行的隔离执行体

`runtime_bridge.py` 只负责入口、进程和回复能力，记忆／模型处理放在 `hermes-scoped-memory/isolated_worker.py`，通道不直接操作数据库。桥接由可信启动代码构造并注入适配器，配置标志不能自证安全：

```python
worker = SandboxedWorker(social_home, domain_id="social-example", policy_revision=1,
                         network_reviewed=True)
bridge = ProcessIsolationBridge(worker, private_dispatch=verified_private_dispatch)
adapter = NapCatAdapter(config, isolation_bridge=bridge)
```

`verified_private_dispatch` 必须是宿主的完整私人 turn 回调，仍由宿主管理私人能力；缺失时主人私人路径明确拒绝，不送到社交 worker。普通平台工厂暂不自动注入该回调，因此不能把示例当作生产启用配置。私人的现有 legacy 模式不被改动。

社交 worker 每轮只挂载自己的 home；主模型使用该 home 的 `chat.json` 和权限为 0600 的 `model.key`，不读取主人凭据。`chat.json` 显式指定 OpenAI 兼容 chat endpoint 和 model；只允许 HTTPS，测试可显式开放 127.0.0.1 HTTP。其主对话请求不执行模型工具；私人／共享事实均先按 scope 查询。没有把独立进程本身等同隔离，已使用真实 bubblewrap mount/PID/user namespace 验证私有文件和环境不可见。

这是新增的受限聊天执行路径。它与宿主 `HostExtractor` 的正式自动提取接线分别验证；还没有在一个生产部署中串起所有模块。此 worker 当前归档并提供关键词／公共记忆，不在其中暗建另一套自动云提取 fallback。
