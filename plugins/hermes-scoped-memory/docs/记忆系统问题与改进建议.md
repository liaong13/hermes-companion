# 记忆系统问题与改进建议（早期评估存档）

> 本文是方案评估，不是已完成能力清单，也不是生产启用指令。本次只改中文文档，不修改插件代码、安装依赖、创建 profile、调用模型提取真实群消息或调整生产配置。

> 原路径为 `docs/记忆系统问题与改进建议.md`。保留早期问题分析供追溯；当前方案以 [开发设计](开发设计.md) 与 [OpenRouter 选型](OpenRouter嵌入模型选型.md) 为准，事实以 [开发状态](开发状态.md) 为准。下文“本地 embedding 优先”已被本轮“优先评估 OpenRouter、向量仍存本地”替代；下文依赖缺失是历史检查，未在本轮重新探测。自有文档采用 MIT。

## 已确认的基线

- 当时的私人环境选择 Mem0，使用操作者自己配置的同一主体跨 agent 共享个人记忆；具体主体标识已脱敏，不作为项目默认值。
- 内置 `memory.memory_enabled`、`memory.user_profile_enabled` 都开启；NapCat 使用 `hermes-cli` 工具集。
- `group_sessions_per_user` 已为 `true`，因此不能把“群上下文一定共享”当成当前事实；仍需实测线程、摘要和历史检索路径。
- 新 `scoped-memory` 仅提交源码、未启用，离线测试 32 项通过；当前预检阻挡多人启用。
- 新插件已有本地归档、按用户＋来源隔离、关键记忆 CRUD、中文双字关键词和一跳关联。没有自动提取、向量检索、群公共库、彻底擦除或持久作业队列。
- 本次检查的 Hermes Python 环境没有 numpy、sentence-transformers、FAISS、sqlite-vec、onnxruntime，系统没有 Ollama 命令。不能把候选向量后端说成已就绪。

## 建议总路线

保留私人环境的内置记忆与 Mem0，不为每位群友建 profile；新增一个所有群聊／访客共用的社交信任域，内部仍按用户管理本地记忆。先解决上下文、工具、历史和失败时的准入边界，再接自动提取和混合检索。

同一进程多 profile 只是配置／数据路径隔离；不等于文件、进程或操作系统沙箱。开放不受信任成员前，需要受限运行服务或独立系统账号／容器的边界设计，并验证消息转交，不重复启动抢占同一 OneBot 连接。

## 1. 自动语义提取尚未实现（功能优先级高）

**问题**：目前只有主对话主动写关键记忆，模型漏调用就没有可召回的摘要。全量归档不等于形成有效记忆。

**建议**：本地原文落盘后写持久提取任务。明确“记住”、偏好变更、计划／事实纠正可优先；普通对话按轮次、空闲或话题结束批处理。抽取器只接收同一允许范围的窗口及必要旧事实，绝不整库输入。

优先使用官方 `ctx.llm.complete_structured` 或异步对应接口，注入到提供者中，注册专用辅助任务，不直接读取凭据或伪造 SDK 接口。插件仍需本地强制校验 JSON Schema，不能仅依赖模型输出有效 JSON。模型无工具、无写库权限，只返回候选：主体、陈述者、事实类型、内容、来源消息／证据片段、事件时间、关联人／主题／事件、置信等级、是否替代旧事实。

身份和可见范围由程序强制绑定，模型不能授予访问权或扩大范围。明确陈述可进入有效候选；引用、玩笑、第三人转述、推测、敏感资料先待确认或不入长期事实。助手自己的猜测不能变成用户事实。提取失败只标记待重试，不能补造结果。

**待评估**：使用现有主模型做后台批处理，还是另选便宜／本地提取模型？建议先接现有宿主接口验证准确性，成本统计后再选择专用模型。若主模型在云端，额外提取请求也会出站，必须明确接受这条数据路径。

## 2. 只有字面匹配，没有向量检索（功能优先级高）

**问题**：同义改写容易漏召回；字面词重合也可能引入无关记录。

**建议**：本地中文 embedding＋SQLite 向量扩展作为首选验证方向。候选 `BAAI/bge-small-zh-v1.5`，模型卡声明 MIT、面向中文检索；优先评测 CPU／ONNX 路线，但 ONNX 产物来源、许可证、输入前缀、池化、归一化及量化误差都要验证，不能默认随便一个导出可用。模型缓存和可选运行依赖与主 Hermes 环境隔离，不因升级插件强装一套 PyTorch。

向量只索引有效关键记忆／事件摘要，不默认嵌入全部原文。SQLite 保留权威内容与索引状态；每个向量附模型标识、修订／维度、文本哈希。模型变化建立影子索引、验证后切换，不混用不同模型向量。

采用 sqlite-vec 时，授权范围作为支持的元数据条件参与 KNN；不先查全库 Top-K 再过滤，也不默认每位低频群友都建立碎片分区。扩展不可用时退回已有关键词，不影响归档。

**待评估**：建议本地 embedding 优先；云 embedding 仅在用户同意成本及内容出站后启用。当前未下载／实测模型，不能承诺延迟或准确率。

## 3. 缺少统一混合召回与“事件接续”（功能优先级高）

**建议流程**：

```text
可信用户／来源与可见范围
→ 当前话题＋少量允许的近期上下文
→ 关键词路与向量路并行
→ RRF 排名融合
→ 关联人物／事件的一跳扩展
→ 状态过滤、去重、相关性阈值
→ 按预算注入少量关键事实
→ 必要时沿来源读取原文片段
```

首次先用 SQLite 关联表，不引入独立图数据库。人物名称不能合并为同一账号；别名与匿名事件要保留各自稳定 ID。关联扩展必须保持权限谓词，不能沿关系跳到别人的私聊。可选 reranker 延后，用实测判断收益而不是一开始堆模型。

**验收**：使用合成中文问法／同义改写／同名人物／时间冲突／无关查询建评估集，比较关键词与混合方案的命中、错误召回和耗时。不能只证明“返回了结果”。

## 4. 内置记忆先于插件加载（上线阻挡）

**问题**：插件只管外部提供者；私人 USER／MEMORY 已经进入系统提示词时，之后拒绝 Mem0 也不能撤回。

**推荐**：私人 default 保持原内置记忆及 Mem0；社交信任域不开私人内置注入，只加载审核后的公共 SOUL／规则以及 scoped-memory 本地路径。无需为每个人建 profile。当前提供者对任何环境都要求关闭内置注入，属于首版保守门槛；不要为迎合它而直接关闭主人 default，下一版应明确支持“社交 local-only 模式”，不复制 Mem0 凭据、也不需要初始化主人后端。

Hermes 有官方多 profile 与 `gateway.profile_routes`，本机 matcher 支持 chat_id、user_id；但未检查到按 chat_type 直接匹配的字段。建议显式列出允许群和主人私聊、拒绝未知路由，不能配置一个过宽的 user_id 规则导致主人在群里也回私人域。

同进程方案适合受控接线验证，不是最终强沙箱。更高安全要求使用独立服务／系统账号／容器和经验证的分发边界；单独建立 profile 不会自动阻止宿主文件读取。

**备选**：只用一个 profile，关闭全局内置注入，改由受控服务按可信身份注入主人资料。会影响 CLI、缓存、镜像及现有使用方式，也更依赖宿主接入点，因此不作为首选。

## 5. 工具与历史可绕过记忆权限（上线阻挡）

**问题**：当前 NapCat 使用 hermes-cli；有 unrestricted terminal/read_file/session_search 时，模型可以绕开 scoped-memory 直接读库、凭据或全局历史。

**建议**：私人域保留技术工具；社交域默认只开放聊天必需工具及受控记忆接口，明确限制 terminal、文件、全局 session_search、凭据访问、技能写入和可触发特权执行的委派／定时／管理命令。需要历史时提供同群／当前用户的受控历史工具，不给全库搜索。

工具白名单由宿主强制；公共运行账号／容器不能挂载主人 home、Mem0 凭据或私有 state.db。不能只依靠提示词“不要读取”。对 web 等仍需审核可调用范围和信息出站。

## 6. 缺少群公共记忆（协作能力缺口）

**问题**：当前同一群中每个人仍只能读自己的记录，无法自然接续多人共同讨论的事件。

**建议**：保留个人库，另加本群公共事件库与参与关系。不把“群内出现过的一切”自动公开为长期画像；公共项目／群规／约定可由明确请求或保守规则进入群库。私人偏好只有允许时作为群可见资料。

每条记录区分 subject、asserted_by、participants、visibility、source；“A 说 B 明天来”不是 B 本人已确认。允许发言者修正自己的陈述；不能让任意人覆盖他人记录。冲突并列、标待确认，不自动编造共识。

当前用户问公共项目时可读本群有效公共事件；本人私聊仍默认不带入群。公开范围由可信规则决定，模型抽取只能建议不能授权。

## 7. 会话、摘要及旧缓存还需端到端审计（上线阻挡）

当前 `group_sessions_per_user=true` 已有正面基础，不需要重复“开启”它。但要测试线程、引用、压缩摘要、历史搜索和恢复后归属。公共话题可经群公共摘要补充，不必立刻把所有人的完整聊天合到同一会话。

切换前备份旧私人文件和状态；切换后为社交路由建立干净会话／重建缓存 agent。不能仅改配置后沿用已装入私人信息的上下文，也不能擅自清空所有历史。

## 8. 提供者失效时宿主仍可能继续聊天（上线阻挡）

**建议**：在构建社交 agent 之前验证路由、最小工具权限和无私人上下文。安全前提失败就拒绝进入不安全域，不能退回 default／主人提供者。

安全隔离前提满足时，单纯本地记忆服务故障可以降级为“无记忆聊天”，但必须显式状态、停止写入并保留待重试作业；绝不能借故障改用主人 Mem0。守卫需选择已验证能强制拒绝的接入点，普通忽略返回值的观察钩子不算拦截。

## 9. 内存队列不可靠，尚无恢复流水线（可靠性优先级高）

**建议**：允许的原文及 outbox 任务在同一事务内持久落盘。提取／向量任务携带不可变用户／来源／修订号，按 source_id、窗口修订和模型版本形成幂等键。工作状态有 pending/running/done/failed、重试次数及租约；启动时恢复未完成任务，磁盘错误明确告警。

回复不能等待长时间模型提取；最小落盘动作有界，后台计算有并发、超时与重试上限。SQLite 多表／向量索引要有一致性检查、备份和可重建索引；不声称跨外部服务恰好一次。

## 10. 删除只是软状态，不能真正忘记（隐私优先级高）

**建议**：分开“归档”“纠正”“彻底删除”。默认长期保留允许原文；有效事实被新状态替代后退出默认召回但保留历史。明确要求忘记时撤除事实、来源正文、向量、词索引、关联、缓存与待处理任务，避免后台再次生成。

向用户说明备份、WAL／日志和外部 Mem0 的删除边界；可用保留策略或备份轮换，但不承诺已经清掉第三方备份。删除只影响有权对象，群共同事件需检查其他参与者资料及公共记录规则。

## 11. 预算字段名与实际单位不符（体验与兼容性）

`max_injection_tokens` 当前是字节预算。建议改为明确 `max_injection_bytes`，兼容读取旧配置并警告，不静默改变单位；需要 token 上限时新增真实分词器计数，分词器不可用明确降级。默认只注入少量事实，工具原文按需分页；原文保留量与每轮上下文量分开管理。

同时对召回耗时、原文读取、候选数量、提取窗口和模型费用设独立上限。阈值先在评估集上调，不用未经测量的高精度宣称。

## 12. 启用、兼容性与验收未完成（上线流程）

- 现有插件读取内部 ContextVar 及 Mem0 `_backend.get`，需固定支持范围、提供升级兼容测试；新 local-only 社交模式尽量不接触 Mem0 内部接口。
- 提取、embedding、索引、准入守卫模块化放在现有插件，除非独立部署确有需要，不再拆出大量小插件。
- 使用新的隔离测试 home 和合成数据先做迁移／恢复／提取／向量测试，再做经批准的真实 QQ 多账号测试。自动化测试不能代替真实平台与云调用。
- 真实验收包括主人私聊可用、主人在群里不读私人池、同名／改名、多用户并发、跨群、群公共事件、私聊泄露尝试、失效降级、重置／压缩和重启恢复。
- 全部自有代码与文档 MIT；第三方依赖、模型、ONNX 产物各自审查许可证，不直接搬 AGPL 实现。

## 建议实施顺序与待决定项

1. 先确认私人／社交信任域、群公共记忆规则与可接受的云端提取范围。
2. 优先完成准入、上下文／工具／历史隔离，保持现有白名单不变。
3. 持久作业、来源和纠正机制，再接自动结构化提取。
4. 本地 embedding＋混合检索、相关性评估与故障降级。
5. 完整删除、备份恢复、端到端验收；用户批准后再部署／重启／逐步开放。

建议默认：保留 default＋一个公共社交域；本地中文 embedding；提取初期复用宿主模型但批处理并明确出站；群公共事实保守写入；原文默认长期保留、明确忘记可撤除。以上待用户评估，不代表已选定或已实施。

## Codex 协作方式

用户评估后可通过 tmux 交互式 Codex 编写代码。启动前确认实际命令、工作区和权限；提供真实会话名、cwd、日志及 `tmux attach -t <实际会话名>`，允许用户查看／接管。避免同时启动两个写入同一文件的 agent。不自动授权修改生产配置、读取私有历史、推送未验收代码或重启网关；每批由主任务审查 diff、运行测试再报告。

本轮没有启动编码会话，先提交方案供评估。
